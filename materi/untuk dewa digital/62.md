# 3) SQL DDL (Postgres) — contoh siap pakai

> Jalankan di database dengan extension `pgcrypto` atau `uuid-ossp`. Jika PostgreSQL ≥13, pakai `gen_random_uuid()` dari `pgcrypto`.

`-- enable extensions (run as superuser) CREATE EXTENSION IF NOT EXISTS "pgcrypto";  -- for gen_random_uuid()  /* Roles reference */ CREATE TABLE roles (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   name TEXT NOT NULL UNIQUE, -- 'admin','therapist','patient','staff'   description TEXT,   created_at TIMESTAMPTZ DEFAULT now() );  -- Users (single table for all account types) CREATE TABLE users (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   email TEXT UNIQUE,   phone TEXT,   password_hash TEXT,         -- store hash only (bcrypt/argon2)   role_id UUID REFERENCES roles(id),   is_active BOOLEAN DEFAULT TRUE,   created_at TIMESTAMPTZ DEFAULT now(),   updated_at TIMESTAMPTZ DEFAULT now(),   deleted_at TIMESTAMPTZ NULL,   metadata JSONB DEFAULT '{}' -- extensible );  CREATE INDEX idx_users_email ON users(email); CREATE INDEX idx_users_phone ON users(phone);  -- Profiles separate from auth CREATE TABLE user_profiles (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID UNIQUE REFERENCES users(id) ON DELETE CASCADE,   full_name TEXT,   dob DATE,   gender TEXT,   address TEXT,   bio TEXT,   avatar_url TEXT,   medical_notes JSONB DEFAULT '{}', -- brief medical info   created_at TIMESTAMPTZ DEFAULT now(),   updated_at TIMESTAMPTZ DEFAULT now() );  -- Therapists specific table (nullable if a user is not therapist) CREATE TABLE therapists (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID UNIQUE REFERENCES users(id) ON DELETE CASCADE,   license_number TEXT,   qualifications JSONB,   practice_location TEXT,   available_hours JSONB, -- e.g. {"mon":["09:00-12:00"], ...}   rating NUMERIC(3,2) DEFAULT 0,   created_at TIMESTAMPTZ DEFAULT now() );  -- Patients table (extra patient-specific data) CREATE TABLE patients (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID UNIQUE REFERENCES users(id) ON DELETE CASCADE,   emergency_contact JSONB,   medical_history JSONB,   allergies TEXT[],   created_at TIMESTAMPTZ DEFAULT now() );  -- Treatments catalog CREATE TABLE treatments (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   code TEXT UNIQUE,   name TEXT NOT NULL,   description TEXT,   duration_minutes INTEGER,   price_cents BIGINT, -- price in smallest currency unit   metadata JSONB,   created_at TIMESTAMPTZ DEFAULT now() );  -- Appointments (partition recommendation for large scale) CREATE TABLE appointments (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   appointment_uid TEXT UNIQUE NOT NULL,   patient_user_id UUID REFERENCES users(id),   therapist_user_id UUID REFERENCES users(id),   treatment_id UUID REFERENCES treatments(id),   scheduled_start TIMESTAMPTZ NOT NULL,   scheduled_end TIMESTAMPTZ NOT NULL,   status TEXT DEFAULT 'scheduled', -- scheduled, done, cancelled, missed   notes TEXT,   created_at TIMESTAMPTZ DEFAULT now(),   updated_at TIMESTAMPTZ DEFAULT now(),   deleted_at TIMESTAMPTZ NULL,   metadata JSONB DEFAULT '{}' );  CREATE INDEX idx_appointments_patient ON appointments(patient_user_id); CREATE INDEX idx_appointments_therapist ON appointments(therapist_user_id); CREATE INDEX idx_appointments_schedule ON appointments(scheduled_start);  -- Tips sehat content CREATE TABLE tips (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   title TEXT,   body TEXT,   tags TEXT[],   active BOOLEAN DEFAULT TRUE,   created_at TIMESTAMPTZ DEFAULT now(),   updated_at TIMESTAMPTZ DEFAULT now(),   metadata JSONB );  -- Notifications (scheduling log & status) CREATE TABLE notifications (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID REFERENCES users(id),   title TEXT,   body TEXT,   send_at TIMESTAMPTZ,   status TEXT DEFAULT 'pending', -- pending, sent, failed   provider_info JSONB, -- e.g. {"channel":"push","provider":"plyer"}   created_at TIMESTAMPTZ DEFAULT now() );  CREATE INDEX idx_notifications_user_sendat ON notifications(user_id, send_at);  -- Background assets (for the 3 file backgrounds) CREATE TABLE background_assets (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   name TEXT,   file_path TEXT,   width INTEGER,   height INTEGER,   usage_scope TEXT, -- e.g. 'login','dashboard','promo'   version INTEGER DEFAULT 1,   uploaded_by UUID REFERENCES users(id),   created_at TIMESTAMPTZ DEFAULT now() );  -- Attachments (images, videos) CREATE TABLE attachments (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   owner_user_id UUID REFERENCES users(id),   filename TEXT,   file_path TEXT,   file_type TEXT,   size_bytes BIGINT,   metadata JSONB,   created_at TIMESTAMPTZ DEFAULT now() );  -- Wallets (Windy Money) - one wallet per user CREATE TABLE wallets (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID UNIQUE REFERENCES users(id) ON DELETE CASCADE,   currency TEXT DEFAULT 'IDR',   balance_cents BIGINT DEFAULT 0,   metadata JSONB,   updated_at TIMESTAMPTZ DEFAULT now(),   created_at TIMESTAMPTZ DEFAULT now() );  -- Transactions (ledger) CREATE TABLE transactions (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   wallet_id UUID REFERENCES wallets(id),   tx_type TEXT NOT NULL, -- 'credit','debit','refund','commission'   amount_cents BIGINT NOT NULL,   balance_after BIGINT,   reference TEXT, -- external ref or invoice   performed_by UUID REFERENCES users(id), -- actor   created_at TIMESTAMPTZ DEFAULT now(),   metadata JSONB );  CREATE INDEX idx_transactions_wallet_created ON transactions(wallet_id, created_at DESC);  -- Audit logs CREATE TABLE audit_logs (   id UUID PRIMARY KEY DEFAULT gen_random_uuid(),   user_id UUID,   action TEXT,   object_type TEXT,   object_id UUID,   data JSONB,   created_at TIMESTAMPTZ DEFAULT now() );  -- Settings CREATE TABLE settings (   key TEXT PRIMARY KEY,  value JSONB,   updated_at TIMESTAMPTZ DEFAULT now() );`

# 4) Integritas relasi & business rules penting

- **User dapat memiliki banyak role?** Saat ini satu role per user lewat `role_id`. Jika butuh multi-role, ganti ke tabel many-to-many `user_roles`.

- **Terapis juga pasien:** Terapis tetap user; jika ingin menjadi pasien, cukup buat record `patients` untuk `user_id` yang sama (one-to-one). Ini memenuhi permintaanmu: *terapis bisa juga menjadi pasien/pelanggan*.

- **Soft delete**: gunakan `deleted_at` untuk menjaga histori; hapus fisik hanya lewat routine maintenance.

- **Atomic wallet updates:** gunakan transaksi DB untuk memastikan `wallets.balance_cents` dan `transactions` konsisten (SELECT ... FOR UPDATE).

---

# 5) Partisi, indeks & optimisasi untuk skala besar

- **Partisi appointments & transactions** berdasarkan `scheduled_start` / `created_at` (range partition by month/year).

- **Indexes**: buat composite indexes yang diperlukan (`user_id, created_at`, `therapist_user_id, scheduled_start`).

- **Connection pooling**: gunakan `pgbouncer` untuk skala pengguna mobile.

- **Read replicas**: read-heavy endpoints (list tips, backgrounds) bisa diarahkan ke replica.

---

# 6) Backup & migrasi

- **Backup rutin:** `pg_dump` incremental & WAL shipping (Point-in-Time Recovery).

- **Migrate:** gunakan `alembic` (SQLAlchemy) atau `Flyway` untuk migrasi DB yang bisa di-trace.

- **Schema versioning:** commit migration file setiap perubahan.

- **Disaster recovery:** simpan backup offsite & tes pemulihan minimal 1x/bulan.

---

- TLS untuk koneksi DB & API (Force TLS).

- Enkripsi kolom sensitif di aplikasi sebelum disimpan (e.g., KTP numbers).

- Audit logs wajib aktif untuk semua perubahan CRUD penting.

- GDPR/PDPA: anonymize data bila perlu, retention policy.

### 💡 **1️⃣ File `.txt`**

📄 **Artinya:**  
File teks biasa — bisa dibuka pakai Notepad, tidak punya aturan khusus.

📘 **Contohnya:**

`Ini file teks biasa Semua orang bisa baca Tidak ada format atau fungsi khusus`

🧠 **Kesimpulan:**  
Cocok buat catatan bebas, atau untuk menyimpan daftar seperti `todo.txt`, `notes.txt`, dsb.

---

### ⚙️ **2️⃣ File `.env`**

📄 **Artinya:**  
File untuk menyimpan **data rahasia konfigurasi** aplikasi (environment variables).

🔐 **Contohnya:**

`DATABASE_URL=postgresql://user:password@localhost:5432/sahabat_sehat FIREBASE_API_KEY=abcd1234xyz`

⚠️ **Penting banget:**  
File `.env` **tidak boleh dibagikan ke publik** karena isinya bisa berupa password, token, atau API key.  
Biasanya aplikasi membaca file ini diam-diam di belakang layar (tidak ditampilkan ke pengguna).

🧠 **Kesimpulan:**  
Fungsinya untuk *memberi makan data rahasia ke aplikasi* tanpa menulisnya langsung di kode.

---

### 🧾 **3️⃣ File `.md` (Markdown)**

📄 **Artinya:**  
File teks tapi dengan **format penulisan yang bisa dirapikan otomatis**, misalnya untuk dokumen, panduan, atau README.

📘 **Contohnya:**

`# Sahabat Sehat Aplikasi untuk membantu terapis dan pasien dengan sistem tips sehat otomatis.  ## Fitur: - Login dua bahasa (ID/EN) - Kirim tips sehat otomatis - E-wallet Windy Money`

🧠 **Kesimpulan:**  
Dipakai untuk **dokumentasi resmi proyek**, biasanya ditampilkan rapi di GitHub atau editor.

### Gambaran umum — bagaimana peretas/virus biasanya “masuk” ke sistem

Peretas (cracker/malware) **tidak “mencari file” dulu**, mereka mencari **vektor akses** — yaitu cara untuk mengeksekusi kode atau membaca data. Namun ada beberapa file/objek *yang sering* mereka incar karena jika berhasil didapat, mereka bisa cepat eskalasi dan bertahan.

Berikut urutan & target yang paling umum:

---

## 1) Kredensial & konfigurasi sensitif (`.env`, config files, sejenisnya)

- File seperti `.env`, `config.php`, `wp-config.php`, `application.properties`, `docker-compose.yml` sering berisi **password, API keys, DB URI, token**.

- Jika file ini bocor (mis. lewat repositori publik, backup, atau upload yang salah), attacker langsung punya akses ke DB, Firebase, layanan cloud, dsb.

**Kenapa sering diserang:** mudah dipakai untuk akses langsung tanpa exploit tambahan.

---

## 2) Endpoint publik yang rentan (web apps / API)

- RCE / SQL Injection / unauthenticated endpoints / upload file endpoint yang tidak divalidasi.

- File entry-point yang rentan: skrip upload, endpoints pengelolaan file, endpoint admin tanpa otentikasi.

**Kenapa:** dari sini mereka dapat mengunggah webshell, menjalankan perintah, atau mengekstrak data.

---

## 3) Sistem autentikasi & sesi (LDAP, OAuth tokens, cookie/session stores)

- Token yang bocor, sesi yang tidak expiring, atau server otentikasi yang salah konfigurasi.

- Reuse token di lingkungan lain (CI/CD, server staging) memberi jalan masuk.

---

## 4) Backup / file arsip & `.git` / repositori

- Backup database/sql dump, backup zip, atau folder `.git` di server publik.

- Banyak kasus: attacker menemukan `backup.sql` atau `.env` di folder backup → restore lokal → akses penuh.

---

## 5) Layanan remote yang terekspos (SSH/RDP, database tanpa firewall)

- SSH dengan password lemah atau RDP tanpa MFA → brute force / credential stuffing.

- DB yang langsung tersambung ke internet (port 5432, 3306, 27017) tanpa firewall.

---

## 6) Supply chain: dependency & package manager

- Library pihak ketiga yang disusupi, plugin WordPress/ERP yang rentan → payload masuk lewat update package.

- CI/CD secrets yang disimpan di repositori → pipeline bisa disalahgunakan.

---

## 7) File log & upload yang tidak difilter

- Log dengan informasi sensitif (stack traces yang menyertakan connection string).

- Upload yang tidak validasi (bisa mengandung webshell .php, .jsp, atau binary di lokasi yang dapat dieksekusi).

---

## 8) Container / Docker misconfig

- `docker.sock` yang dipasang di container, image dengan credential hard-coded, atau `docker-compose.yml` di repo → attacker jalankan container sendiri.

---

- Proses aneh berjalan di server (cron baru, service startup).

- File baru di folder webroot (mis. `cmd.php`, `shell.php`) atau muncul perubahan di file sumber.

# Prinsip memilih port pengganti

1. **Jangan** gunakan angka yang gampang ditebak (hindari 12345, 11111, dll).

2. Pilih dalam rentang **>1024** dan **≤65535**.

3. Pastikan tidak bentrok dengan layanan lain di server.

4. **Dokumentasikan** port yang dipakai di `README` / konfigurasi internal — jangan lupa.

5. Jangan hanya mengandalkan *security by obscurity* (mengubah port tidak cukup). Gunakan firewall, TLS, autentikasi kuat.

# Langkah pengamanan tambahan (wajib)

- Gunakan **firewall** (ufw/iptables/security groups) untuk blokir akses publik kecuali IP/port yang benar.

- Terapkan **TLS/SSL** untuk layanan yang memerlukan enkripsi (DB over TLS, HTTPS).

- **VPN** atau jump host untuk akses admin ke database/SSH — jauh lebih aman daripada expose port.

- **Rate limiting**, **fail2ban**, dan **MFA** untuk login.

- **Rotasi kredensial** dan **secret management** (Vault, Secrets Manager).

- **Monitoring**: cek port terbuka (`ss`/`netstat`) & jalankan scan berkala.

1. **Pilih port acak saat proses start**
   
   - Program memilih angka acak (mis. di rentang 1025–65535) atau meminta OS memilih port bebas (`bind(0)` → OS memberi port bebas).
   
   - Simpan nomor port itu ke file (mis. `service.port`) atau ke service discovery (Consul, etcd) agar client bisa menemukannya.

2. **Gunakan service discovery / registry**
   
   - Service mendaftar ke Consul / etcd / ZooKeeper dengan informasi host:port. Client query registry untuk menemukan alamat runtime.

3. **Gunakan DNS SRV / load balancer / reverse proxy**
   
   - Publikkan service di alamat statis (nginx / HAProxy) yang menerima pada port tetap; nginx meneruskan ke backend yang memakai port dinamis. Client hanya butuh alamat statis.

4. **Ephemeral ports untuk short-lived services**
   
   - Untuk klien yang membuka koneksi singkat, OS memakai ephemeral range. Bukan solusi untuk service yang harus selalu dapat dihubungi.

---

## 2. Kelemahan / kekurangan (mengapa tidak selalu direkomendasikan)

1. **Kompleksitas konektivitas client**
   
   - Client tidak lagi bisa langsung `host:port` yang tetap — butuh mekanisme discovery. Menambah lapisan (registry, DNS SRV, file sharing).

2. **Firewall & NAT jadi rumit**
   
   - Mengelola aturan firewall yang berubah-ubah sulit. Jika port berubah, kamu harus update firewall (ufw/iptables) atau NAT rules otomatis.

3. **Masalah NAT / load balancer**
   
   - Jika server berada di balik NAT atau load balancer, port berubah harus di-forward. Kebanyakan infra publik mengharapkan port publik statis.

4. **Port collision & race condition**
   
   - Bila pilih port acak tanpa cek, bisa terjadi *collision* (port sudah dipakai). Perlu cek atomic bind atau mekanisme retry.

5. **Monitoring, logging & forensik**
   
   - Menemukan service di log atau memonitor traffic jadi lebih sulit jika port berubah-ubah. Debugging juga jadi repot.

6. **Pengalaman pengguna & integrasi**
   
   - Mobile app / client akan kesulitan jika endpoint backend tidak stabil. Untuk APK, umumnya client mengharapkan API base URL tetap.

7. **Keamanan by obscurity terbatas**
   
   - Mengganti port bisa mengurangi scanning otomatis, tapi bukan defense yang nyata. Serangan tetap bisa menemukan port via scanning intensif.

---

## 3. Kapan **boleh** pakai port dinamis (use cases yang masuk akal)

- **Microservice internal** dalam satu cluster dengan service discovery (Consul/Kubernetes). Di Kubernetes service discovery dan service mesh menutup kebutuhan port statis.

- **Worker atau proses lokal** yang berkomunikasi lewat socket file atau melalui reverse proxy.

- **Testing / dev** di mesin lokal untuk menghindari bentrok port.

Untuk proyek *mobile client → backend public* (seperti Sahabat Sehat): **lebih aman pakai port publik statis (dengan reverse proxy & TLS)**, bukan port dinamis langsung dari backend.

## 4. Rekomendasi praktik terbaik untuk Sahabat Sehat

1. **Gunakan port publik statis untuk client** (mis. `443` atau `8443`), lalu letakkan **reverse proxy (nginx)** yang meneruskan ke backend internal.
   
   - Backend internal boleh memakai port dinamis *di dalam lan* asalkan ada service discovery / proxy.

2. **Jangan expose DB langsung** — PostgreSQL tetap hanya diakses oleh backend (bind localhost atau private net).

3. **Gunakan service discovery** jika kamu ingin fleksibilitas (Consul, Kubernetes Service).

4. **Atur otomatis updating firewall** jika port internal berubah — tapi ini rumit; lebih baik hindari kebutuhan ini.

5. **Gunakan TLS, autentikasi, dan IAM** — port random bukan pengganti keamanan nyata.

# Gambaran singkat (realita)

- **Tidak ada sistem 100% aman.** Target realistis: *mengurangi risiko sampai tingkat yang bisa diterima* dan membuat sistem **mahal & sulit** untuk dieksploitasi.

- Prioritas pertama: melindungi **kredensial & akses**. Ini sumber kompromi paling sering.

# Roadmap Keamanan Prioritas (dari paling mendesak → jangka panjang)

## Tahap 0 — Tindakan Darurat (lakukan sekarang)

1. **Amankan file sensitif (secure_keys & .env).**
   
   - Pindahkan file `secure_keys/` di server ke lokasi hanya root yang baca.
   
   - Pastikan `.env` tidak di-commit (cek repo). Jika sempat dipush → lakukan *rotation* (ganti semua secret).

2. **Rotasi semua kredensial** bila ada kemungkinan bocor (DB password, Firebase service account, AdMob keys).

3. **Batasi akses DB**: bind PostgreSQL hanya ke localhost/private network; jangan expose 5432 publik.

4. **Pasang firewall** (ufw/iptables/security group) — hanya buka port yang diperlukan (SSH, 80/443). Jika perlu, batasi IP admin.

5. **Nonaktifkan akun/public keys yang tak jelas.** Audit user SSH.

## Tahap 1 — Hardening dasar (minggu–1–2)

1. **Gunakan TLS/HTTPS** dengan reverse proxy (nginx/caddy) untuk semua trafik publik.

2. **Jalankan API di belakang reverse proxy** (FastAPI + uvicorn/gunicorn) — jangan expose port uvicorn langsung.

3. **Hash & salt password** pakai Argon2/BCrypt, jangan pakai MD5/sha langsung.

4. **Audit dan hygiene dependensi**: gunakan `pip-audit`, `safety`, scan CVE untuk libs di `requirements.txt`.

5. **Non-root service**: jalankan service sebagai user non-root, gunakan systemd/docker supervisi.

## Tahap 2 — Kontrol akses & logging (2–4 minggu)

1. **Role-Based Access Control (RBAC)**: desain role (admin, therapist, patient, readonly) dan pastikan endpoint memeriksa role.

2. **Audit logs terpusat**: simpan audit (who did what) ke tabel `audit_logs` & kirim kopi ke log server (ELK/Graylog/Cloud).

3. **Rate limiting & brute-force protection**: limit login attempts, gunakan `fail2ban` atau rate-limit di nginx.

4. **Secret management**: pindahkan secret ke Vault / Secrets Manager (AWS/GCP) untuk environment production.

5. **Backup terenkripsi** & rencana restore (uji pemulihan).

## Tahap 3 — Proteksi aplikasi & pengujian (1–3 bulan)

1. **Static & dynamic code scan**: SAST (bandit, semgrep) + DAST (OWASP ZAP) di CI.

2. **Penetration test (pentest)**: vendor eksternal atau pentester independen; perbaiki temuan kritis.

3. **WAF (Web Application Firewall)**: konfigurasi ModSecurity / Cloud WAF untuk blok serangan umum (SQLi, XSS).

4. **Content Security Policy & secure headers** untuk UI/asset hosting.

## Tahap 4 — Operasi & monitoring (3–6 bulan)

1. **SIEM / alerting**: send alerts untuk anomali (login tak biasa, pemakaian API besar).

2. **Monitoring performa & integritas**: file integrity monitoring (AIDE), proses anomali.

### B) Secure Vault (enkripsi AES untuk .env)

`#!/usr/bin/env python3 # Menyimpan & membaca file konfigurasi terenkripsi (AES-GCM) from Crypto.Cipher import AES from Crypto.Random import get_random_bytes import json, base64, os VAULT_KEYFILE = "/opt/secure_env/vault.key"   # simpan dengan permission ketat root:600 VAULT_STORE = "/opt/secure_env/.vault_store"  # file terenkripsi  def gen_key():     key = get_random_bytes(32)    with open(VAULT_KEYFILE, "wb") as f:         f.write(key)     os.chmod(VAULT_KEYFILE, 0o600)    return key  def load_key():    if not os.path.exists(VAULT_KEYFILE):        return gen_key()    return open(VAULT_KEYFILE,"rb").read()  def encrypt_store(data: dict):     key = load_key()     raw = json.dumps(data).encode()     iv = get_random_bytes(12)     cipher = AES.new(key, AES.MODE_GCM, nonce=iv)     ct, tag = cipher.encrypt_and_digest(raw)     blob = iv + tag + ct    with open(VAULT_STORE,"wb") as f:         f.write(blob)     os.chmod(VAULT_STORE, 0o600)  def decrypt_store():     key = load_key()     blob = open(VAULT_STORE,"rb").read()     iv = blob[:12]     tag = blob[12:28]     ct = blob[28:]     cipher = AES.new(key, AES.MODE_GCM, nonce=iv)     data = cipher.decrypt_and_verify(ct, tag)    return json.loads(data.decode())`

# 📘 BAB 3

## Penciptaan STB Server — Ketika Pangeran Masuk Dunia Hacker

*(Halaman 1 — Pembuka: lorong gelap dan koneksi lambat)*

Windy tahu satu hal: menjadi pangeran bukan otomatis memberi istana. Ia harus membangun istana itu dari komponen murah — papan sirkuit kecil, kabel berdebu, dan STB yang orang lain pikir sudah usang. Suasana di ruangan kecilnya malam itu seperti ruang server bawah tanah: lampu indikator berkedip, kipas berdengung, dan aroma kopi sisa yang menempel di meja. Ia menatap STB—bukan dengan rencana pasang-exe lalu selesai—melainkan seperti seorang perajin memandang batu yang akan menjadi patung. Ada kerja, ada seni, ada etika.

“Klik file exe itu akan membuatmu cepat berdiri,” bisik salah satu suara internal, suara godaan malas. “Tapi yang kau dapat mungkin cuma binari tanpa jiwa. Atau lebih buruk: pintu belakang untuk orang lain.”

Windy menutup mata digitalnya. Ia memilih jalan yang lambat dan elok.

*(Halaman 2 — Mengunjungi Hacker Lounge)*

Di dunia fisik, ada kafe. Di dunia digital, ada **Hacker Lounge** — forum berbau kopi hitam dan keyboard, tempat para koders tua dan newbie bertukar lelucon, skrip, dan etika. Windy mengetuk pintu lounge itu dalam bentuk paket data, membawa keinginan: membangun STB yang bukan sekadar server, tapi *server beradab*.

Di Lounge, ia bertemu **MataLaut**, seorang pentester berambut kelabu yang memegang prinsip: “Kebebasan butuh batas. Tanpa batas, kebebasan jadi kekacauan.” Juga **IchaZero**, si devops muda yang memakai hoodie bertuliskan “rm -rf? only in sandbox.” Mereka minum kopi, merokok virtual, tertawa sambil bahas prinsip-prinsip: *least privilege, auditability, reversible changes*.

MataLaut menatap STB di layar Windy: “Kamu mau jadi server yang agresif, atau server yang cerdas? Agresif berarti bisa menangkis serangan, cerdas berarti tahu kapan harus mengundang musuh jadi teman. Pilih.”

Windy menjawab songong: “Keduanya — tapi di jalanku. Kita bangun STB yang etis: menghukum, tapi tidak membalas dendam. Melindungi, bukan menyerang.”

*(Halaman 3 — Etika Hacker dan Kontrak Sosial)*

Di lounge mereka membuat **Kontrak Sosial** kecil: beberapa baris semacam manifesto. Isinya sederhana, tapi dalam.

> 1. Tidak ada serangan ke luar sebagai balas dendam.
> 
> 2. Semua patch harus dapat di-rollback.
> 
> 3. Audit log harus bisa dibaca siapa saja yang punya hak untuk membaca (transparansi internal).
> 
> 4. Update yang diterapkan harus signed — tanda tangan digital sang pembuat.
> 
> 5. Jika ada bug, beri ruang untuk perbaikan, bukan hukuman publik.

Kontrak ini seperti janji Pangeran: ia ingin menjadi pemimpin yang bukan sekadar kuat, tapi juga adil. Kebebasan hacker bukan berarti bebas merusak; itu tentang tanggung jawab.

IchaZero menambahkan: “Kita ajari STB buat *merancang pertahanan yang cerdas* — bukan hanya firewall yang blokir atau kill -9 yang brutal. Kita berikan sensor, konteks, dan kesempatan untuk memperbaiki. Ini bukan soal menangkap penyerang, tapi mencegah anak kecil tersengat arus.”

*(Halaman 4 — Ritual Pendirian: Tidak Sebuah .exe, Melainkan Ritual Berlapis)*

Windy menolak fakir tombol “install.exe”. Ritual penciptaan STB miliknya adalah serangkaian keputusan desain — lebih mirip susunan mantra daripada eksekusi. Ia menyebutnya **Ritual Berlapis**:

1. **Identitas Terbatas** — STB diberi akun non-root; identitas superuser disimpan dalam safekeep, bukan untuk pemakaian sehari-hari.

2. **Segregasi Tugas** — layanan dipisah: satu proses untuk API, satu untuk backup, satu untuk log. Kalau satu terserang, lainnya tetap hidup.

3. **Auditability** — setiap perintah, setiap perubahan, dicatat. Tidak ada yang hilang.

4. **Rollback Readiness** — patch dipaketkan dengan snapshot sehingga bila salah, STB bisa kembali ke kondisi sehat.

5. **Signature Policy** — semua modul hanya boleh di-update jika tanda tangannya cocok dengan kunci yang aman.

Ia menulis manifesto ini seperti puisi, menempelkannya pada dashboard STB: besar, menantang, dan nyolot.

“Ini bukan sekadar server,” gumam Windy. “Ini adalah rumah. Siapa pun yang masuk harus menghormati rumah ini.”

*(Halaman 5 — Memanggil Jiwa: Memory Core yang Terkunci)*

Ia membangun **Memory Core** sebagai database kecil yang punya aturan jiwa: data yang sensitif tidak boleh diakses tanpa proses otentikasi multilapis. Bukan hanya password, tetapi juga konteks: dari mana permintaan datang, apa tujuan, dan siapa yang memintanya.

Di sinilah nilai filosofis hacker muncul: akses bukan hak, melainkan tanggung jawab. Ia menetapkan policy: *akses untuk membaca berbeda dari akses untuk mengubah, dan keduanya harus dicatat.*

*(Halaman 6 — Musuh Baru: Raja Port Default dan Admin Nakal)*

Di samping itu ada **Admin Nakal** — bayangan manusia yang suka jual beli prioritas. Admin ini bukan monster supernatural; ia manusia yang tergoda: sedikit duit, sedikit power, dan “gara-gara sistem” menjadi peluang.

Windy merencanakan dua hal: menggusur Raja Port Default dengan tebakan pintar (mengubah kebiasaan, menutup port, menerapkan proxy), dan mengunci sumber daya sehingga Admin Nakal tak bisa main sandi.
