## Gambaran singkat

**Device Owner / MDM** = mode di mana aplikasi kamu diberi hak istimewa pengelolaan perangkat (mirip aplikasi “kantor” di perusahaan). Dengan hak ini aplikasi bisa **mengontrol kebijakan perangkat** (mis. membatasi aplikasi, mengunci perangkat, mengatur layar, policy Wi-Fi/Network dalam cakupan Device Owner, menginstall/disable app, remote wipe, dsb) — jauh lebih kuat daripada aplikasi biasa.  
Karena kekuatan besar itu, Android **membatasi bagaimana sebuah app bisa menjadi Device Owner** (agar tidak disalahgunakan).

---

## Apa yang bisa dilakukan (contoh kemampuan untuk parental control / remote)

Dengan *Device Owner* kamu bisa (bergantung versi Android & implementasi OEM):

- Menetapkan app sebagai **kiosk / single-app mode** (mencegah user membuka app lain).

- **Membatasi daftar aplikasi yang boleh dijalankan** (whitelist/blacklist).

- Mencegah uninstall aplikasi pengelola.

- Menjadwalkan waktu aktif aplikasi / mengunci layar pada jam tertentu (via policy + alarm).

- **Mengunci screen / memaksa logout**, menonaktifkan kamera, memodifikasi keyguard/lockscreen features (tergantung versi).

- Memerintahkan **wipe data** (remote factory reset) dalam kasus kompromi.

- Mengirim perintah remote dan menerima status via push (FCM) — mis. “matiakan internet”, “close app X” (implementasi detail tergantung API yang tersedia).

- Menginstall/disable aplikasi secara remote (MDM mampu instal app dari private repo).

> Catatan: hak-hak di atas *lebih kuat* dibanding app biasa, tetapi detail API & izin bisa berbeda antar versi Android dan vendor (Samsung/MIUI/Huawei punya variasi).

---

## Keterbatasan & hal yang perlu diperhatikan

- **Perlu proses enrollment khusus** untuk menjadikan app sebagai Device Owner. Ini *bukan* sekadar minta permission dari user — ada prosedur provisioning (seringkali memerlukan factory reset atau provisioning token).

- Beberapa tindakan (mis. mematikan mobile data) *tidak selalu tersedia* di semua versi Android secara langsung — MDM dapat mengelola konfigurasi via policy, tapi beberapa toggle mungkin bergantung OEM.

- Jika app Device Owner dibuat secara salah (atau server kamu bocor), risikonya besar (kontrol penuh atas perangkat). Keamanan server & auth wajib sangat kuat.

- Karena potensial disalahgunakan, beberapa metode provisioning butuh akses fisik atau konfigurasi awal dari admin (bukan remote murni tanpa setup).

---

## Cara umum membuat & men-deploy solusi Device Owner (alur tinggi, non-kode)

1. **Rancang arsitektur remote-control utama**
   
   - **Backend (server)**: kecil, aman, mengirim perintah ke device — biasanya menggunakan *push* (Firebase Cloud Messaging / FCM) untuk command delivery. Server otentikasi, log, UI admin.
   
   - **Aplikasi Android (client)**: menerima push command, verifikasi signature / token, lalu memanggil API DevicePolicyManager untuk mengeksekusi aksi (lock, set-permission, whitelist app, dsb).
   
   - Komunikasi: *push (FCM)* untuk perintah real-time + *periodic polling* (fallback). Semua traffic pakai TLS; token sensitif disimpan aman (Android Keystore).

2. **Buat aplikasi Android yang mendukung Device Admin / Device Owner**
   
   - Implementasikan `DeviceAdminReceiver` (device admin callback).
   
   - Tambahkan metadata & manifest entries yang dibutuhkan untuk device admin (file xml device-admin).
   
   - Implementasikan handler untuk perintah remote (receiver untuk FCM) lalu menerjemahkan ke panggilan `DevicePolicyManager`.

3. **Provisioning / Menjadikan app Device Owner**  
   Ada beberapa metode, pilih salah satu:
   
   - **ADB provisioning (developer / test)** — sering dipakai saat development/testing:  
     contoh (konsep): `adb shell dpm set-device-owner "com.package.name/.Receiver"`  
     (perintah ini *umumnya mengharuskan* perangkat dalam keadaan factory-reset atau kondisi provisioning tertentu).
   
   - **QR code / NFC / Zero-touch provisioning** — Android Enterprise menyediakan mekanisme provisioning untuk menjadikan app sebagai Device Owner di perangkat baru tanpa ADB; lebih cocok untuk deployment massal.
   
   - **Manual via Settings (Device admin, lesser privilege)** — untuk mode Device Admin biasa (bukan Device Owner), user dapat mengaktifkan app sebagai device admin lewat Settings → Security → Device admin apps — ini *tidak sama* dengan Device Owner (kekuatan lebih kecil).

4. **Implementasikan mekanisme remote command delivery**
   
   - Gunakan **FCM**: server kirim pesan data payload ke device; aplikasi client memvalidasi pesan (signature/hmac) lalu panggil API DevicePolicyManager.
   
   - Pastikan server memerlukan autentikasi admin (2FA), audit log, rate limit, dan enkripsi.

5. **Keamanan**
   
   - **Server keys**: simpan di vault (mis. secret manager), jangan di-commit.
   
   - **Mutual auth / signed commands**: setiap perintah dapat ditandatangani & dicek di device untuk mencegah spoofing.
   
   - **Audit & revoke**: bila device dicurigai atau token bocor → revoke token &/atau remote wipe.
   
   - **Privasi & hukum**: untuk parental control, jelaskan kebijakan privasi ke anak (sesuai usia) dan patuhi hukum setempat.

## Praktikal: apa yang harus kamu siapkan sekarang (step-by-step, tanpa kode)

1. **Putuskan scope kontrol** (mis. hanya batasi aplikasi & waktu, atau juga pengaturan jaringan, uninstall protection, remote wipe?). Mulai dari kecil.

2. **Persiapkan perangkat pengujian** (1 HP Android untuk testing). Siapkan backup & ketahui cara factory-reset.

3. **Pilih stack**:
   
   - **Client app**: sebaiknya native Android (Kotlin/Java). Meskipun kamu suka Kivy, fitur Device Owner & integrasi manifest/receiver jauh lebih mudah & andal di native. (Kivy dapat digunakan, tapi menambah kompleksitas pada manifest & provisioning).
   
   - **Server**: ringan (Flask/FastAPI/Node.js) yang kirim FCM messages; simpan cred di `.env` / secret manager.

4. **Rancang flow enrollment**: apakah kamu mau
   
   - *manual via ADB* (bagus untuk 1–10 perangkat), atau
   
   - *QR/NFC/zero-touch* (bagus untuk lebih banyak perangkat, lebih rumit konfigurasi).

5. **Buat aplikasi sample** (development): implement `DeviceAdminReceiver` & handler FCM (terima perintah & log actions).

6. **Uji provisioning** dengan device cadangan: coba set-device-owner (ADB) lalu kirim beberapa perintah aman (lock screen, set permitted apps).

7. **Audit & harden**: pastikan server & app log tidak memaparkan secret, gunakan masking, rotasi kunci.

---

## Alasan kenapa aku sarankan **native Android** untuk Device Owner

- Device Owner memerlukan **manifest entries, broadcast receiver, policy xml** dan sering perlu akses tingkat rendah. Native SDK (Kotlin/Java) punya dokumentasi & API langsung untuk `DevicePolicyManager`.

- Kivy / Python-for-Android mungkin bisa, tapi menambah lapisan kompatibilitas (pembedahan manifest, buildozer hooks). Untuk project parental control serius: native lebih cepat & lebih sedikit bug.

---

## Risiko & Etika

- Mode Device Owner memberi kontrol besar. Gunakan hanya pada perangkat yang **kamu miliki atau dengan izin jelas** (mis. gadget anak yang kamu beri).

- Hindari praktik pengintaian berlebihan (merekam pesan, mengambil screenshot tanpa izin) — selain ilegal di banyak tempat, itu merusak kepercayaan. Parental control idealnya adalah kombinasi kontrol teknis + komunikasi dengan anak.

- Pastikan kamu dapat melepaskan control (un-enroll) jika perlu.

# Fitur 1 — WA aman (whitelist kontak + blokir media)

**Kendala teknis utama**

- WhatsApp memakai E2E encryption — **kita tidak bisa membaca isi pesan** di server pihak ketiga. Kita hanya bisa mencegah/menyaring dari sisi perangkat (preventive controls), bukan inspeksi pesan.

- Karena itu solusi terbaik: **batasi siapa yang bisa menghubungi** dan **kontrol setelan WA** (auto-download off).

**Pendekatan yang bisa diterapkan**

1. **Device Owner + Kiosk/whitelist apps**
   
   - Tetapkan hanya sejumlah aplikasi yang diizinkan: WhatsApp (atau versi terbatas), SMS, telepon, app sekolah. Ini mencegah instal app baru.

2. **Kontak whitelist**
   
   - Hapus semua kontak kecuali yang kamu setujui, atau paksa kontak device agar hanya berisi daftar yang diizinkan. (Device Owner bisa mencegah user menambah kontak).
   
   - Alternatif: sediakan mekanisme approval (anak minta kontak baru → kamu approve dari admin portal → server kirim perintah ke device untuk menambah kontak).

3. **Blokir auto-download media**
   
   - Tweak pengaturan WhatsApp: default WA punya opsi “Media auto-download” — kita perlu memastikan setting ini OFF. Karena pengaturan app hanya di UI, cara andal:
     
     - Pada provisioning, otomatis set WA setting via accessibility scripting (fragile) *atau*
     
     - Gunakan **managed configuration** jika WhatsApp mendukung Android Enterprise managed configurations (lebih rapi) — butuh WhatsApp enterprise support (tidak selalu tersedia).

4. **Penanganan file/attachment**
   
   - Matikan penyimpanan otomatis ke galeri (setelan WA).
   
   - Buat service monitoring file system (folder Downloads / WhatsApp/Media) yang menahan/memindahkan file media masuk ke quarantine folder untuk di-review sebelum user boleh membuka. (Butuh permission storage — Device Owner bisa atur).

5. **Interaksi & approval flow**
   
   - Notifikasi: jika ada file masuk dari nomor non-whitelist, app client menahan file dan kirim notifikasi ke akun orang tua (push/notification). Orang tua approve → file dilepas.

**Batasan & catatan**

- Tidak mungkin *menyensor isi pesan WA* tanpa mem-bypass E2E (tidak etis/illegal). Fokus di preventive controls (kontak, media, pemasangan app).

- Jika anak memakai WA Web atau ganti nomor di device lain, perlu policy untuk mematikan pairing (Device Owner bisa mencegah WA Web pairing? Bisa memblokir browser atau akses USB debugging).

- Jika kamu memberi anak **nomor seluler sendiri**, atur nomor itu di server admin untuk whitelist dan verifikasi.

# Fitur 2 — GPS lokasi / geofencing

**Cara kerja**

- Aplikasi client (device anak) pakai **Fused Location Provider** (Android) untuk ambil lokasi periodik atau on-demand.

- Lokasi dikirim ke server admin via HTTPS; server menyimpan riwayat (time, lat/lon, akurasi).

- Opsional: geofence rules (mis. jika keluar area sekolah → notifikasi).

**Detail implementasi**

- Interval: configurable (mis. tiap 5–15 menit saat screen on, lebih jarang saat idle untuk hemat baterai).

- Mode: *push on demand* (parent tekan "lokasi sekarang") + *periodic heartbeat*.

- Privacy: simpan hanya yang perlu; enkripsi data at rest; punya retention policy (mis. simpan 30 hari).

- Emergency: tombol SOS di device anak yang kirim lokasi real-time disertai audio/snaps (opsional).

**Batasan & catatan**

- Akurasi tergantung GPS, Wi-Fi, mobile data; indoor akurasi turun.

- Pastikan user consent & pemberitahuan — hukum lokal mungkin mengatur tracking anak di bawah umur.

# Fitur 3 — Batasi waktu bermain (per app) & nonton YouTube

**Kemampuan Device Owner**

- Device Owner bisa:
  
  - Suspends/unsuspends packages (`PackageManager.setApplicationHidden` / `DevicePolicyManager.setPackagesSuspended`) → efektif mem-blacklist sementara.
  
  - Atur **kiosk mode** / *lock task mode* untuk membatasi apps yang boleh dibuka.
  
  - Menyusun jadwal: pada jam tertentu app-game di-suspend; di jam lain di-unsuspend.

- Bisa implementasikan **quota harian** per package dengan UsageStatsManager untuk memantau pemakaian dan enforce limit.

**YouTube khusus**

- Opsi:
  
  - Izinkan hanya **YouTube Kids** (lebih aman).
  
  - Atau block YouTube app, dan sediakan konten curated (video dibundel) dalam app edukasi.
  
  - Kalau child menonton lewat browser, block browser atau disable browsing.

**Implementasi langkah**

1. Client aplikasi memonitor pemakaian aplikasi (UsageStats) → melaporkan ke server atau enforce local rule.

2. Admin UI: set rule per package (contoh: `com.pubg.game` max 60 menit/hari; `com.google.android.youtube` max 30 menit/hari).

3. Saat limit tercapai → Device Owner suspend package atau tampilkan layar “Waktu Habis — Minta Izin”.

## 2) Hal teknis & batasan utama

- **Transport**: gunakan Wi-Fi hotspot (paling stabil & throughput) atau Wi-Fi LAN; Bluetooth cocok untuk jarak pendek dan pesan kecil.

- **Jumlah koneksi**: 5–10 device realistis; lebih banyak mulai menimbulkan masalah throughput, latensi, dan battery drain.

- **Jarak & jangkauan**: jika child keluar jangkauan hotspot/Wi-Fi, komunikasi terputus (perlu reconnect/queue).

## 3) Rancangan arsitektur singkat (recommended)

- **Pairing** (fisik): QR code / PIN pada pemasangan → hasilkan symmetric key, simpan di Android Keystore.

- **Transport utama**: Parent buat **Wi-Fi hotspot**, child connect ke hotspot → parent buka TCP/TLS server socket (listening) → child connect (TLS) → handshake authenticated.

- **Protocol**: ringan, JSON messages, fields: `device_id`, `cmd`, `nonce`, `timestamp`, `signature/HMAC`.

- **Concurrency**: gunakan async socket (asyncio) atau thread pool di Android Service; buat per-client queue.

- **Heartbeat**: tiap child kirim heartbeat tiap 30–300 detik (konfigurable) → parent tahu status koneksi.

- **Command queuing**: jika child offline, simpan per-device command queue di parent (reliable delivery when reconnect).

- **Security**: TLS (self-signed OK for local), message HMAC, keys in keystore.

- **Visibility**: child app tampil notifikasi persist bahwa pengawasan aktif.
